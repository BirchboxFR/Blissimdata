Blissim Analytics – Spécification : Gestion des
Utilisateurs & Droits d'Accès
​2026-09-22 · ​@mathieu
Contexte & objectifs
Blissim Analytics est la future plateforme de reporting hébergée sur Replit, ouverte à la
fois aux équipes Blissim et aux marques partenaires (Redken, Kérastase, etc.).
Cette spec couvre uniquement la gestion des utilisateurs et des droits d'accès :
authentification, rattachement compte/marque/pays, et permissions par page. Le
contenu fonctionnel des pages (KPIs, dashboards) est hors périmètre et sera spécifié
page par page au fur et à mesure de leur création — voir la section Pages, modules et
Packages pour le mécanisme qui absorbe ces ajouts progressifs.
Authentification
Deux profils, deux méthodes :
Un admin est créé directement avec son compte Google @blissim.fr, sans mot de passe à
gérer côté Blissim. Un utilisateur marque est invité par email par un admin : il définit un
mot de passe à la première connexion, ou peut lier son compte Google si l'email
correspond. La réinitialisation de mot de passe se fait par email.
Modèle Compte / Marques
Un Compte (société mère, ex. « L'Oréal ») regroupe une ou plusieurs Marques canoniques
(ex. Redken, Kérastase). Un utilisateur est rattaché à un Compte, et reçoit un accès
explicite à un sous-ensemble des marques de ce compte — pas automatiquement à
toutes : ajouter une marque à un Compte n'ouvre pas l'accès aux utilisateurs existants
tant qu'il n'est pas accordé marque par marque.

Un utilisateur est rattaché à un seul Compte (jamais plusieurs). S'il doit intervenir sur un
second Compte (un autre groupe), on crée un second utilisateur avec un email différent
plutôt que de multiplier les rattachements.
La marque canonique ( brand_id_sublissim ) est l'identifiant pivot utilisé pour les droits.
Chaque pays a sa propre marque locale ( brand_id_local ), reliée à la marque canonique
via une table de correspondance brand_country_mapping , alimentée par la requête
BigQuery déjà en place côté Sublissim :
WITH bsm AS (
  SELECT id, shop_id, brand_id, external_id
  FROM `teamdata-291012.bdd_prod_sublissim.brand_shop_mapping`
  QUALIFY ROW_NUMBER() OVER (PARTITION BY id ORDER BY _airbyte_extracted_at 
DESC) = 1
),
shop AS (
  SELECT id, code
  FROM `teamdata-291012.bdd_prod_sublissim.shop`
  QUALIFY ROW_NUMBER() OVER (PARTITION BY id ORDER BY _airbyte_extracted_at 
DESC) = 1
),
sublissim_brand AS (
  SELECT id, code, name
  FROM `teamdata-291012.bdd_prod_sublissim.brand`
  QUALIFY ROW_NUMBER() OVER (PARTITION BY id ORDER BY _airbyte_extracted_at 
DESC) = 1
)
SELECT b.dw_country_code, b.id AS brand_id_local, b.name AS brand_name_local,
       sb.id AS brand_id_sublissim, sb.name AS brand_name_sublissim, sb.code 
AS brand_code_sublissim
FROM `teamdata-291012.inter.brands` b
JOIN shop sh ON sh.code = b.dw_country_code
JOIN bsm ON bsm.shop_id = sh.id AND bsm.external_id = b.id
LEFT JOIN sublissim_brand sb ON sb.id = bsm.brand_id
ORDER BY b.dw_country_code, b.id
Cette table de correspondance sert de référentiel : quand un utilisateur a accès à la
marque canonique Redken, la plateforme sait quelles lignes locales (par pays) inclure
dans les requêtes BigQuery/GA4.
Cette table est resynchronisée quotidiennement depuis BigQuery, au même rythme que
les tables events_YYYYMMDD .

Droits pays
Le périmètre pays n'est pas figé à FR/DE/ES : il suit dynamiquement tous les codes pays
présents dans la table shop côté Sublissim, pour rester aligné automatiquement si de
nouveaux pays s'ajoutent.
Pour chaque accès (utilisateur × marque), le scope pays est soit une liste explicite de
codes pays, soit la valeur spéciale ALL (tous les pays où la marque est présente).
Exemple : un utilisateur Redken peut voir FR sans voir ES , tandis qu'un autre a ALL sur
Kérastase.
Pages, modules et Packages de droits
Les pages n'existent pas encore toutes : elles seront créées au fil de l'eau. Le modèle doit
donc absorber une nouvelle page sans jamais toucher les droits utilisateur un par un.
Réponse : un registre de pages + des packages réutilisables entre les deux.
L'accès réel d'un utilisateur à une page = union des pages de tous ses packages, plus
d'éventuelles exceptions ponctuelles ( user_page_override ) pour accorder ou retirer
une page sans créer tout un nouveau package.
Quand une nouvelle page est créée, la marche à suivre est toujours la même :

1. Enregistrer la page dans le registre page (id, clé, nom).
2. L'ajouter au(x) package(s) concerné(s) via package_page (ex. l'ajouter à « Marque –
Standard »).
3. Tous les utilisateurs déjà dans ce package voient la page apparaître automatiquement
— aucune action sur les comptes utilisateurs.
Un nouvel utilisateur reçoit un package par défaut selon son profil (Admin → « Admin – Full
», Utilisateur Marque → « Marque – Standard »), ajustable ensuite.
Seuls les admins Blissim créent et modifient les packages et leur contenu ; un utilisateur
marque ne gère pas ses propres droits.

Les admins Blissim ont un accès global par défaut : toutes les marques, tous les pays,
toutes les pages, sans entrée dans user_brand_access .
Parcours utilisateurs clés
Créer un compte marque (ex. L'Oréal)
1. Un admin crée le Compte L'Oréal.
2. Il rattache les marques canoniques concernées (Redken, Kérastase) au compte.
3. Il invite un premier utilisateur par email, lui accorde accès à une ou plusieurs marques
du compte, un scope pays ( FR , ou ALL ), et un package de pages.
Inviter un nouvel utilisateur sur un compte existant
1. L'admin sélectionne le compte, choisit les marques et pays à ouvrir pour ce nouvel
utilisateur.
2. Il assigne un package (par défaut « Marque – Standard »).
3. L'utilisateur reçoit un email d'invitation pour définir son mot de passe ou lier son
compte Google.
Ajouter une nouvelle page à la plateforme
1. La page est développée et enregistrée dans le registre page .
2. Elle est ajoutée au(x) package(s) pertinent(s).
3. Les utilisateurs concernés la voient apparaître sans aucune action manuelle sur leur
compte.
Décisions retenues
Comptes : un utilisateur est rattaché à un seul Compte (jamais plusieurs) ; plusieurs
marques restent possibles au sein d'un même Compte.
Log d'audit : chaque changement de droits (marque, pays, package) est journalisé —
qui, quoi, quand (table audit_log ).
Admins Blissim : accès global par défaut, sans restriction de périmètre.

Expiration des accès : chaque accès porte une date d'expiration optionnelle
( expires_at ), avec retrait automatique à échéance.
Synchronisation brand_country_mapping : quotidienne depuis BigQuery.
Prochaine étape : ce modèle est validé — passer au schéma technique (tables SQL,

Texte minimal : tags/pastilles courts plutôt que des listes à puces complètes — une
carte = une idée.
Bandeau de conclusion : fond lavande très pâle, texte foncé, phrase clé en gras violet —
jamais un bloc violet plein avec texte blanc.
Contenu très dense (comparatifs multi-lignes, projets avec lead/livrables/décision) :
basculer en tableau avec en-tête violet plein plutôt que forcer des cartes.
Beaucoup d'espace blanc, une idée forte par slide, pictogrammes simples style
Feather/Notion.
Footer systématique : « BLISSIM | [titre de la présentation] » en bas à gauche, numéro
de page en bas à droite.
